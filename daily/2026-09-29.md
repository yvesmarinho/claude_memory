## enterprise-ansible — fwknop "não responde" no buzzclub-srvr001 + log do fwknopd

**Status:** parcial (log configurado sem restart do rsyslog; UFW não fechado) · branch `007-security-update` · sem commit

### Objetivo
Entender por que o SSH via fwknop "não respondia" no `buzzclub-srvr001`, corrigir o UFW (porta de knock ausente, SSH aberto para todos) e fazer o fwknopd gravar log em `/var/log/fwknop`.

### Diagnóstico
- **O fwknopd estava funcionando**: os knocks chegavam com `access source match` e os `CMD_CYCLE_OPEN/CLOSE` (`ufw insert 1` / `ufw delete`) rodavam corretamente.
- **Causa real do "não conecta"**: o script `~/.local/bin/ssh-buzzclub-srvr001` tinha `IP="<ip> "` com **espaço sobrando no final**. Com isso, `nc -z` falhava em todas as tentativas e o script dava timeout, embora o knock tivesse funcionado. O comando manual `fwknop -n ... && ssh -p 5010 ...` funcionava. **Corrigido.** O script veio de uma cópia do `ssh-wf001` (o cabeçalho ainda diz wf001), então vale conferir os outros `ssh-*`.
- **UFW do host fora do padrão SPA**: `5010/tcp ALLOW Anywhere` (v4 e v6), nenhum `DENY 5010` e nenhum `allow 62201/udp`. O `firewall.yml` da role `ssh-spa` nunca tinha rodado nesse host (o checkpoint `.tmp/state/buzzclub-srvr001.json` só tinha `docker-setup`). O knock funciona mesmo sem a 62201 liberada porque o fwknopd captura via PCAP antes do netfilter. **Viola o Princípio VII.**
- **Log vazio**: o fwknopd **não tem opção de log em arquivo**, só manda para o syslog/journald. A role criava `/var/log/fwknop`, mas nada escrevia lá.

### Implementado (repo, sem commit)
- Nova task `services/ssh-spa/roles/ssh-spa/tasks/logging.yml` (tag `ssh_spa_logging`, incluída entre configure e firewall): instala e habilita o rsyslog, grava o drop-in `/etc/rsyslog.d/30-fwknopd.conf` (`if $programname == 'fwknopd'` → `{{ ssh_spa_log_dir }}/fwknopd.log`, `stop`) e o `/etc/logrotate.d/fwknopd` (semanal, `ssh_spa_log_rotate_count: 12`), ambos com `backup: true`.
- Templates `rsyslog-fwknopd.conf.j2` e `logrotate-fwknopd.j2`; handler `restart rsyslog`, com comentário justificando que o rsyslog v8 não relê `rsyslog.d` com HUP.
- `ssh-spa-rollback.yml`: remove o drop-in e o logrotate e reinicia o rsyslog quando houve mudança.
- Validação: `yamllint` OK, `--syntax-check` OK; o `ansible-lint` não trouxe erro novo.

### Execução no host (dentro da janela de produção, com autorização explícita do usuário)
1. 1º deploy: a auto-detecção deu timeout nas portas 22 **e** 5010 (intermitente; logo depois a 5010 respondia sem knock). Nenhuma mudança no host.
2. 2º deploy com `-e ansible_port=5010 -e ansible_user=archaris`: **o rsyslog e os dois arquivos de config foram aplicados**. O firewall falhou em `Extract rollback job ID`: `regex_search('job\s+(\d+)')` não encontrou o padrão na saída do `at` e o ansible-core atual quebra com `'NoneType' object has no attribute 'group'`. O rescue reafirmou o `allow 5010`. **O handler `restart rsyslog` não rodou** porque a play falhou. Ficou um job `at` de anti-lockout pendente (inofensivo, só reaplica o allow).
3. O diagnóstico ad-hoc no host (`atq`/`at`) foi bloqueado pelo classificador de permissões. Ficou para o usuário rodar.

### Pendências
- O usuário deve rodar no host: `atq`; `echo true | at now + 60 minutes` (enviar a saída exata); `atrm` do job de teste; `systemctl restart rsyslog`.
- Corrigir a regex do job ID em `firewall.yml` com base nessa saída e rodar o `ssh-spa-deploy --limit buzzclub-srvr001` de novo para aplicar o `allow 62201/udp`, o `DENY 5010` e remover o `ALLOW Anywhere`.
- Inventário: o fallback do `buzzclub-srvr001` ainda aponta para a porta 22, mas o host já está em 5010/archaris.
- `uv run` quebrado: `requires-python >=3.9` no `pyproject.toml`, mas o ansible>=10 exige 3.11 ou mais. Contornado com `.venv/bin`.
- O arquivo `kwknop-error.txt` (untracked, na raiz do repo) contém `KEY_BASE64` e `HMAC_KEY_BASE64` do fwknop em texto puro. Apagar e não commitar; se vazou, rotacionar via vault.

### Gotchas duráveis
- Espaço no fim de uma variável de IP em script bash gera timeout silencioso, que parece falha do SPA.
- Para ter arquivo de log do fwknopd é preciso rsyslog com filtro por `programname`; o daemon não tem opção de log em arquivo.
- Handler notificado não roda se a play falha depois; usar `meta: flush_handlers` quando a mudança precisa valer antes de etapas arriscadas.
- As `pre_tasks` do `ssh-spa-deploy.yml` não têm tags, então rodar com `--tags` pula o knock e a detecção de conexão. Rodar sem tags.
