# 2026-09-15

## 🎯 Sessão — enterprise-ansible: correções pós-onboarding (branch `007-security-update`)

### ✅ Concluído

**Revisão de segurança do UFW/fwknop (continuação do onboarding de `buzzclub-srvr001`)**:
- **Checkpoint (`.tmp/state/<host>.json`) fora do lugar**: `common/{load,save}-execution-state.yml` usavam path relativo puro — para tasks `delegate_to: localhost`, o Ansible resolve isso contra o diretório do *playbook de entrada*, não a raiz do repo. `site-first-deploy.yml` (em `./playbooks/`) gravava em `./playbooks/.tmp/state/`, fragmentando o checkpoint por playbook em vez de ser único por host. Corrigido: path ancorado em `{{ inventory_dir }}/../.tmp/state/` (magic var estável, sempre `./inventories`). Checkpoint órfão antigo apagado.
- **`ssh_whitelist_ips_archaris`/`archyros` em `group_vars/all/security.yml`** tinham faixas RFC1918 (`127.0.0.1`, `192.168.x.x`) — sem rota nenhuma até um VPS público, davam falsa sensação de restrição. Removidas, só ficou o IP público real (`177.11.48.73`).
- **`ufw_additional_services` (PostgreSQL/MySQL) era global** em `group_vars/all/security.yml`, abrindo 3306/5432 em **toda a frota** via `site-first-deploy`. Movido para `host_vars/wfdb02/main.yml` (único host com banco nativo, sem Docker).
- **Bug crítico em `services/ssh-spa/roles/ssh-spa/tasks/firewall.yml`**: a task "Enable UFW" usava `community.general.ufw: policy: allow` sem `direction` — confirmado no código-fonte do módulo (`ufw.py`) que isso aplica a mudança à direção `incoming` por padrão, **sobrescrevendo permanentemente o `ufw_default_incoming: deny`** da role `vps-security`. Ou seja: toda vez que `ssh-spa-deploy` rodava, a política padrão de entrada do UFW virava `allow` — o oposto do modelo "porta fechada por padrão" (Constituição Princípio VII). Removido; o anti-lockout já era coberto por outros mecanismos (allow temporário de SSH + job `at` de rollback).

**`docker-install.yml` reescrito para casar com o padrão de checkpoint + SPA já usado em `site-first-deploy`/`ssh-spa-deploy`**:
- **Bug real encontrado via log**: o playbook nunca fazia knock SPA nem detectava porta/usuário em runtime — travava indefinidamente em `Gathering Facts` contra hosts já protegidos por fwknop (a porta SSH fica fechada por padrão), sem erro nenhum até o timeout de 600s do `ansible.cfg`. Corrigido: `gather_facts: false` + knock SPA (`failed_when: false`, no-op seguro em hosts sem fwknop) + `common/detect-connection`, mesmo padrão de `ssh-spa-deploy.yml`.
- Adicionado checkpoint de execução (`.tmp/state/<host>.json`) na role `docker-setup` — evita reinstalar Docker do zero em host que já tem.
- **Dois bugs colaterais do checkpoint pulando a role, achados rodando de verdade contra `buzzclub-srvr001`**:
  - `register` numa task com `when` **sobrescreve a variável mesmo quando pulada**, com um dict mínimo `{"skipped": true}` sem `stdout_lines`/etc. — quebrava o template de resumo (`docker_installation_summary.j2`) mesmo a role tendo rodado direitinho antes. Padrão de correção: comando roda sempre num var temporário (`_docker_verify_check` etc.), e um `set_fact` condicional (que não sofre esse efeito colateral) decide se promove pro nome final.
  - `defaults/main.yml` de uma role (`docker_user`, `docker_groups`, `docker_packages`...) só é carregado quando a role roda via `include_role` — se o checkpoint pula a role, essas vars ficam indefinidas e quebram o resumo/relatório final. Corrigido com um `include_vars` incondicional do `defaults/main.yml` da role no início do playbook.

**PR #5** (`007-security-update` → `main`, https://github.com/yvesmarinho/enterprise-ansible/pull/5) atualizado com 2 commits desta e da sessão anterior.

### ⚠️ Aprendizados / gotchas

- `community.general.ufw` com `policy`/`default` **sem `direction`** aplica à direção `incoming` por padrão (ver `ufw.py`: `current_default_values[direction or 'incoming']`) — nunca usar `policy:`/`default:` num módulo `ufw` só pra "garantir que está habilitado" sem pensar na direção; é fácil sobrescrever o default policy sem perceber.
- Path relativo em task `delegate_to: localhost` (ex.: `.tmp/state/...`) resolve contra o diretório do **playbook de entrada**, não a raiz do repo nem o CWD do `ansible-playbook` — usar `{{ inventory_dir }}/../...` pra ter um único destino estável entre playbooks diferentes.
- `register: X` numa task com `when: false` **ainda sobrescreve `X`** com um dict de resultado "skipped" mínimo — nunca confiar que uma task pulada preserva o valor anterior da variável registrada. Se o objetivo é "definir só se ainda não definido", usar `set_fact` com `when: X is not defined` (esse sim não sofre o efeito colateral), alimentado por um var temporário coletado incondicionalmente.
- `defaults/main.yml` de uma role só é carregado quando ela é de fato incluída (`include_role`/`roles:`) — um playbook que pula a role condicionalmente (checkpoint, `when`, etc.) mas ainda referencia as vars dessa role em `post_tasks`/templates precisa de um `include_vars` explícito do `defaults/main.yml`, incondicional.
- Diagnóstico via log de playbook "parado": task `Gathering Facts` sem erro nenhum por minutos = quase sempre SSH não conseguindo abrir conexão (porta fechada, SPA não aberto) — não é bug de lógica, é falta de knock/detecção antes do gather.

- **Regressão encontrada e corrigida na mesma sessão**: a primeira revisão
  trocou os headers por um middleware compartilhado (`security-headers@docker`,
  definido só em `containers/traefik`) — isso quebrou aplicações reais em uso
  (router com middleware "não encontrado" quando esse container específico não
  está no ar = rota inteira desativada, não só falta de header). Corrigido
  para middleware próprio por serviço (self-contained), e reinserido
  `forceSTSHeader` (removido por engano — esse campo continua válido no v2/v3,
  diferente de `SSLRedirect`/`SSLHost`).

### ⚠️ Aprendizados / gotchas

- Docker Compose **não resolve `${VAR}` em chaves do YAML**, só em valores —
  um nome de serviço `${PROJECT_NAME}:` é literal, não um erro silencioso sutil,
  é um compose que nunca funcionaria.
- Referenciar um middleware Traefik definido nas labels de **outro**
  container/compose (`nome@docker`) acopla a disponibilidade de cada serviço
  dependente à daquele container específico — se ele cair, for recriado sem
  aquela label, ou o serviço subir em outra rede/host, o router fica inválido
  e a aplicação fica **totalmente inacessível**, não é degradação parcial.
  Prática mais segura para templates reutilizáveis: middleware self-contained
  por serviço, mesmo que gere alguma duplicação de labels.
- Nem toda label "antiga" do Traefik é obsoleta: `SSLRedirect`/`SSLHost` foram
  removidas do v2/v3, mas `forceSTSHeader` continua um campo válido — checar
  cada campo individualmente na doc atual antes de remover em lote por
  parecerem do mesmo grupo.

## 🎯 Sessão — buzzclubhub: deploy Docker+Traefik em homologação, bug de healthcheck, projeto Supabase dev descoberto

### ✅ Concluído

**Deploy via Docker + Traefik**: `docker/docker-compose.yml` reescrito seguindo o
modelo de `containers/modelo-traefik` (devops-containers) — rede externa `web`,
labels `traefik.*`, sem publicar porta no host, host `dev.buzzclub.co`. Nginx
mantido no Dockerfile (decisão do usuário). Compose não builda mais a imagem —
só `up` a partir da imagem já construída por `scripts/docker-build.sh`
(corrigido nesta sessão: tinha resíduo de projeto Rails, agora usa os
`VITE_SUPABASE_*` corretos via `.secrets/supabase-dev.env`).

**Bug de healthcheck corrigido**: container ficava `unhealthy` mesmo com nginx
de pé e escutando em `0.0.0.0:80` (confirmado via `ps aux` +
`/proc/net/tcp`) — causa era `wget -qO- http://localhost/` no `HEALTHCHECK`
do Dockerfile: BusyBox/musl resolve `localhost` via IPv6 primeiro, nginx só
escuta IPv4, e esse `wget` não faz fallback pra IPv4. Corrigido para
`http://127.0.0.1/`. Como o provider Docker do Traefik exclui containers
unhealthy do roteamento **sem erro visível**, isso explicava o serviço sumir
do dashboard apesar de "Up" no `docker compose ps`.

**Projeto Supabase de homologação descoberto**: `.secrets/supabase-dev.env`
aponta pra um projeto diferente do de produção (`uftbeshtcbydrtohpywe` vs
`emwjhtaxqpbbtayfcjxn`) — resolve pendência aberta desde 12-13/09. Projeto
existe e está ativo, mas com **schema vazio** (nenhuma migration aplicada,
confirmado via `404 PGRST205` ao consultar `/rest/v1/clients`).

**Discussão — cópia de dados produção→dev**: usuário confirmou que as duas
contas Supabase estão sob controle do mesmo diretor da empresa, autorizando a
cópia. Não executada ainda — falta a `service_role` key ou connection string
do Postgres de produção (só há anon key em `.secrets/production.env`, que é
bloqueada pelas mesmas RLS policies validadas em
`security-regressions.test.ts`).

### ⚠️ Aprendizados / gotchas

- `wget`/`curl` do BusyBox (Alpine/musl) contra `localhost` dentro de
  container com serviço IPv4-only: a tentativa IPv6 falha e **não há
  fallback automático** — usar `127.0.0.1` explícito em HEALTHCHECKs.
- O provider Docker do Traefik remove containers `unhealthy` do roteamento
  silenciosamente (não aparece como erro no dashboard) — ao debugar "serviço
  sumiu do Traefik", checar `docker inspect --format='{{json .State.Health}}'`
  antes de qualquer outra hipótese de rede/label.
